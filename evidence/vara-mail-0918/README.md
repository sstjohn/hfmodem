# A Winlink message over VARA, 2026-09-18

One recording of one QSO: W9SSJ working the Winlink gateway KB8AY on 40 m, and a
message crossing. Every transmission in it from this end was generated by the
VARA implementation in this distribution — `hfmodem.kestrel.vara` — driving an
FT-891. No vendor modem software ran at this station.

## Both stations are in the one file

This is the speaker audio, not a transmit-only tap, so it is the whole QSO on a
single clock and nothing has to be aligned against anything. Two rig behaviours
put it there. Incoming RF is muted while the radio is keyed, as it should be. And
this radio can play a transmission back over the same speaker while it is being
sent; that monitor was on for this session. So the recording never goes quiet:
our own transmissions fill our overs, and they are the loudest passages in the
file because the monitor is louder than a received signal. KB8AY's frames sit at
receive level, and band noise sits between.

KB8AY is therefore not audible during our overs. The link is half-duplex and it
was not transmitting then, so nothing is missing — the file holds every
transmission either station made, each in its own turn.

The modem's own decode input for the same session was recorded separately, and is
not here. It correlates with this recording at r = 0.938 at a lag of 22.1 s —
matching the two start times — so it is a shorter, differently-gained window on
the same audio. It is omitted as a duplicate rather than withheld; it lives at
`logs/onair/20260918T154908Z-W9SSJ-KB8AY.wav` in the operator's private record.

## What crossed

Winlink B2F, after the VARA link came up:

```
mail: we said:  ;FW: W9SSJ
mail: we said:  [Pat-1.0.0-B2FHM$]
mail: we said:  ;PR: ########
mail: we sent:  FC EM NL03TXWQ8SGL 633 441 0
mail: we sent:  F> 64
mail: peer sent: FS Y
mail: peer sent: FF
mail: we sent:  FQ
```

Message ID `NL03TXWQ8SGL`, 633 bytes rendered, 441 bytes on the wire after
compression, sent in two blocks. `FS Y` is KB8AY accepting the proposal and `FF`
is the far end reporting it has everything it wanted; both came from the gateway.
`F> 64` is the proposal block's checksum.

The session's own summary line read *"our FQ not sent"* while the frame
transcript above shows `FQ` sent and the session closing on it. The transcript
was right: `summarize()` carried an inverted ternary that printed the negative
on exactly the sessions that had sent a close. `session.our_fq` is set on the
same statement that encodes the frame, so the flag was never wrong — only the
sentence reporting it. Fixed after this recording was made; the log reproduced
above is the one the session wrote, left as written.

One thing this recording does not settle, stated rather than smoothed over: the
operator reports that the message arrived in the addressed inbox. That is a
report, not something in this audio.

The operator believes this is the first Winlink message carried end to end over
HF by an independent implementation of VARA. That is a claim about what other
people have done, which no recording can establish; it is written down here as
their belief and nothing below rests on it.

## Checking it

The digest in `provenance.json` is of the file as shipped:

```
shasum -a 256 20260918T154839Z-W9SSJ-tap.wav
```

The receiver that read this session ships too, so the handshake can be recovered
from the audio directly. `demod_burst` turns a window of samples into tone
indices and `best_match` scores them against the tone sequence a callsign keys:

```python
import wave, numpy as np
from hfmodem.kestrel.vara import vara_frames as VF, vara_mfsk as MK

with wave.open("20260918T154839Z-W9SSJ-tap.wav") as w:
    a = np.frombuffer(w.readframes(w.getnframes()), "<i2") / 32768.0

for kind in (VF.connect_request("2300"), VF.connect_response("2300")):
    n = (len(kind.preamble) + kind.n_payload) * MK.STRIDE
    last = -9.0
    for at in range(0, len(a) - n, int(0.02 * MK.FS)):
        cs, m, N = VF.best_match(MK.demod_burst(a[at:at + n], kind),
                                 ["KB8AY", "W9SSJ"], kind)
        t = at / MK.FS
        if m == N and t - last > 1.0:          # one line per burst, not per window
            print(f"{t:7.2f}s  {kind.name:<17} {cs}  {m}/{N}")
        if m == N:
            last = t
```

That prints seven connect-requests addressed to KB8AY between 31.00 s and 58.70 s,
all 31/31 tones exact, and one connect-response for KB8AY at 60.62 s, 15/15 exact.
The session log for this arm records exactly seven keyed asks — one
connect-request and six retries — and then one received connect-response read at
15/15. The seven are ours; the eighth is KB8AY's, since an initiator never keys a
connect-response. The link came up on the connected-ack that follows it.

The payload frames are OFDM rather than these tone bursts, and reading the
message bytes back out of the recording needs the full receive path, not this
scan. `packages/hfmodem/hfmodem/tests/kestrel/` is where the worked examples of
both live.
